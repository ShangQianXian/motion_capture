# v0.3.3 动捕精度核查与输入归一化

验证日期：2026-09-15（承接 v0.3.2 固定左前 45°）。

本篇记录一次针对「动捕数据与参考视频有差距」的定量核查。**核查推翻了最初的两项判断**，因此这里同时保留正确的结论与作废的结论，避免后来者重复走同一条错路。

## 1. 结论摘要

| 项目 | 结果 |
|---|---|
| 素材相机方位角 | 拟合 **42.0°**，结果记录 **40.0°** → `left_front_45` 设置正确 |
| 三维结果 vs 二维检测重投影中位差 | **5.5 px**（p90 15.3 px） |
| 二维检测自身抖动（二阶差分中位） | **4.3 px** |
| 重建精度结论 | 结果与素材在检测噪声范围内一致，**重建侧已无提升空间** |
| 重定向方向误差（Blender 实测） | **0.0°**（头、双脚、大腿、小腿） |
| 重定向落点误差（Blender 实测） | 左踝累计 **6.5 cm**、右踝累计 **7.3 cm** |
| **偏移的真正来源** | **目标骨架与素材人物的骨长比例不一致**（骨架高 29%，且大腿偏长小腿偏短） |

因此 v0.3.3 **没有**加入"三维重投影精修"阶段（实测只会变差，见 §4），加入的是**度量与告警**（§5）；而"左脚偏移"已定位到重定向比例（§6）。

## 2. 为什么最初判断错了

初期对账脚本用「骨骼在屏幕横向基上的分量」去比「检测到的二维骨长」，漏掉了屏幕纵向分量，于是得到"骨盆宽 +11 px、大腿 +19 px 系统性偏长"的结论。改用完整二维投影距离后，同一份数据的比例是：

| 骨段 | 投影 2D / 实测 2D |
|---|---:|
| hip.L–hip.R | 0.99 |
| shoulder.L–shoulder.R | 1.00 |
| ankle.L–ankle.R | 1.00 |

即投影与检测一致到 1%。**旧的"逐骨偏差表"作废，不要再引用。**

## 3. 输入归一化（保留项，默认关闭）

### 事实

`MotionBERTLabel.encode` 的二维归一化是 `x / w * 2 - 1`，其中 `w` 是**图像宽度**；而 `pipeline` 过去把整帧原图交给 lifter，且 `inference_pose_lifter_model(..., norm_pose_2d=False)`。于是网络看到的尺度完全由"人物占画面多大"决定：

| 素材情况 | 归一化后幅度 |
|---|---:|
| H36M 训练分布 | ≈ 1.0 |
| 本仓库 192 帧行走素材（1344×768，人高 573 px） | 0.85 |
| 1080p 中占 23% 的人物 | 0.28 |
| 人物几乎充满 1000×1000 画面 | 1.8 |

官方实现（MotionBERT `lib/utils/utils_data.py` 的 `crop_scale`）把整段序列按 bbox 归一化到 [-1, 1]，MMPose 自己的 `pose3d_inferencer` 也走 `norm_pose_2d` 路径。本仓库两者都没做。

### 实现

`backend_worker/pose3d_motionbert.py` 新增 `canonical_rebase()` 与 `lift(..., input_normalisation=...)`：

- `canonical` 把整段序列仿射重定基到 H36M 统计 bbox（`center=(528, 427)`、`scale=400`，来自 `mmpose/.mim/configs/_base_/datasets/h36m.py`），并把 `image_size` 一并换成规范尺寸，使 encode 与 decode 用同一个 `w/h`。
- **整段共用同一个缩放因子**，不逐帧归一化：视在大小变化是单目唯一可用的深度线索，逐帧归一化会把它抵消掉。这也是官方 `crop_scale` 的做法。
- 关键点与 bbox 一起重定基，避免二者落在不同坐标系。

### 实测收益（`tools/benchmark_lifter.py`）

已知三维 → 已知相机 → 加 3 px 高斯噪声 → 真实 lifter → 与真值对比。
完整结果在 `.cache/lifter-benchmark.json`，命令：

```powershell
.\.venv\Scripts\python.exe tools\benchmark_lifter.py --kind walk --windows 2 --scenes all
```

| 场景 | 人物占长边 | 模式 | 归一化后幅度 | MPJPE(对齐) | 骨长误差 | 深度 MAE |
|---|---:|---|---:|---:|---:|---:|
| 1344×768，占 57%（本素材） | 57% | current | 0.85 | **0.0545 m** | 0.56 | 0.287 m |
| 同上 | | canonical | 1.00 | 0.0623 m | 0.76 | 0.295 m |
| 1920×1080，占 46% | 46% | current | 0.52 | **0.0511 m** | 0.33 | 0.294 m |
| 同上 | | canonical | 1.00 | 0.0621 m | 0.76 | 0.295 m |
| 1920×1080，占 23% | 23% | current | 0.26 | 0.155 m | 2.26 | 0.272 m |
| 同上 | | canonical | 1.00 | **0.0606 m** | **0.72** | 0.295 m |
| 1000×1000，占 90% | 90% | current | 1.80 | 0.137 m | 3.19 | 0.701 m |
| 同上 | | canonical | 1.00 | **0.0627 m** | **0.75** | 0.295 m |

**判读**：

- `current` 在归一化幅度 0.5–0.9 之间表现最好（0.051–0.055 m）；幅度掉到 0.26 或涨到 1.8 时明显劣化（0.12–0.16 m，骨长误差 2–3 倍）。
- `canonical` 把幅度固定在 1.0，**在所有场景下都稳定在 0.061–0.063 m**，对取景不再敏感。
- 本素材的幅度是 **0.85**，正处在 `current` 的甜点区，所以 canonical 在这里既不改善也不明显变差（0.0545 → 0.0623 m）。

**因此默认仍是 `current`**，并把 `canonical` 做成 UI 选项（**二维输入尺度**，位于“素材与生成”面板中 `素材相机视角` 下方）：

- **跟随画面比例（推荐）** = `current`；人物占画面长边 50%–90% 时精度最好。
- **规范尺度（人物偏小时用）** = `canonical`；对取景不敏感，人物占画面不足约 45% 或几乎充满画面时明显更稳。

它是**捕捉设置**：改动会让已有结果失效并要求重新生成（与 `素材相机视角`、`动作类型` 同一处理），因为提升网络的输入端不同会产出不同的三维结果。判断自己的素材该用哪一档，用上面的基准量一次，不要凭直觉。

（深度 MAE 一列在各模式下都在 0.27–0.30 m 之间，说明提升本身对绝对深度不敏感，改的是姿态形状与骨长一致性。）

## 4. 作废项：三维重投影精修

原计划在提升后加一层"把三维投影回二维观测并修正深度"的阶段。实测（真实 192 帧缓存）表明它只会变差：

| 方案 | 重投影中位差 |
|---|---:|
| 原始结果 | **5.7 px** |
| 上述精修（含骨长约束） | 9.0 px |
| 修正投影模型后的精修 | 11.4 px |

原因是 §1 那个数字：结果已经在检测噪声内，任何"修正"都在拟合噪声；而骨长约束会把本该更准的关节拉向序列中位数。

**不要重新引入这一层**，除非上游发生变化（更准的检测、多视角、真实相机内参）。

## 5. 保留项：重投影诊断与深度主导告警

`backend_worker/reprojection.py`（worker 侧，numpy/scipy，延迟导入）：

- 扫描方位角与焦距／深度，拟合素材实际相机；拟合值与 `capture_transform.applied_yaw_degrees` 相差超过 15° 时告警 `CAMERA_AZIMUTH_CONFLICT`（视角设置填错会被抓住，而不是藏在"看起来还行"里）。
- 逐关节重投影残差；中位差超过 25 px 时告警 `REPROJECTION_HIGH`——**这是整条链路的精度天花板**，任何下游都不可能比"三维与像素的一致程度"更准。
- 逐关节"沿相机光轴位移占比"；占比 ≥ 0.8 且位移 ≥ 0.1 m 时告警 `DEPTH_DOMINANT_MOTION`。单目下沿光轴位移不可观测，这类关节的横向落点来自模型先验，必须让用户知道，而不是假装是观测。

诊断结果写入 `preview_manifest.json` 的 `diagnostics.reprojection`。诊断失败不会让捕捉失败。

离线复算（不需要模型）：

```powershell
.\.venv\Scripts\python.exe tools\validate_reprojection.py .cache\v03-camera
```

## 6. 已定位：偏移来自重定向的比例，不是重建

重投影一致只证明"横向与纵向落点对"，**不能证明沿光轴深度对**。核查结果指向别处：**目标骨架与素材人物的比例不一致**。

`tools/validate_rig_proportions.py`（真实 Blender 4.5.0 + Rigify 生成骨架实测）：

| 骨段 | 素材 | 重定基后应有 | 骨架实际 | 比值 |
|---|---:|---:|---:|---:|
| thigh.L | 0.398 | 0.492 | 0.536 | **1.090** |
| shin.L | 0.384 | 0.475 | 0.454 | 0.957 |
| thigh.R | 0.393 | 0.485 | 0.536 | **1.105** |
| shin.R | 0.385 | 0.476 | 0.454 | 0.955 |
| upper_arm.L | 0.271 | 0.335 | 0.289 | 0.860 |
| forearm.L | 0.231 | 0.286 | 0.263 | 0.921 |
| spine | 0.525 | 0.649 | 0.462 | **0.712** |
| shoulder width | 0.349 | 0.431 | 0.351 | 0.813 |

`root_scale = 1.236`（骨架骨盆高 1.010 m / 素材骨盆高 0.817 m），骨架站高 1.980 m、腿占 50.0%；素材人物约 1.53 m。**骨架比素材人物高约 29%，而且腿部比例偏"大腿长、小腿短"**——`_root_scale` 按骨盆高整体缩放，正好抵消不了这种段内比例差。

实际落点差距（同一关节头对齐后，骨架末端 vs 素材末端，192 帧）：

| 骨链 | 源关节 | 中位差距 | 最大差距 |
|---|---|---:|---:|
| thigh_fk.L | hip.L→knee.L | 0.044 m | 0.044 m |
| shin_fk.L | knee.L→ankle.L | 0.021 m | 0.021 m |
| thigh_fk.R | hip.R→knee.R | 0.051 m | 0.051 m |
| shin_fk.R | knee.R→ankle.R | 0.022 m | 0.022 m |

**左腿逐段累计 4.4 + 2.1 = 6.5 cm，右腿 5.1 + 2.2 = 7.3 cm。** 两条腿长短不同，所以左右偏移量不同——这与"从正面看左脚偏移"的现象一致，也是"左右不对称"的来源。

同一份结果的方向误差是 **0.0°**（`tools/validate_orientation_blender.py`：头、双脚、大腿、小腿全部 0.0°）。也就是说：**重定向的方向传得完全正确，偏差全部来自骨长**。

结论：**继续改重建或后处理不会有收益**。要消除这 6.5 cm，只能在重定向一侧解决——把目标骨架的骨长比例对齐素材（方案 A），或者在写入后按素材关节位置做一次末端位置校正（方案 B）。A 会改变角色的外形轮廓，B 不会。

## 7. 方案 B：足部落点校正（已实现，默认开启）

`blender/foot_ik.py`：方向写完后，按素材的脚踝位置重新求解每条腿。

**做法**：以素材脚踝（按重定向同一比例缩放后的绝对位置）为目标，用骨架自己的大小腿长度做两骨 IK。髋保持重定向给的位置，**膝盖是唯一能动的关节**——髋和脚都定死之后，比例不匹配的腿不可能让膝盖也回到原位。弯曲平面取自素材膝盖相对髋踝轴的偏移，并跨帧带记忆，避免腿伸直时膝盖翻转。

**实测（真实 192 帧 + Rigify 生成骨架）**：

| 指标 | 只传方向 | 足部校正 |
|---|---:|---:|
| 左踝落点偏差（中位） | 11.6 cm | **3.2 cm** |
| 右踝落点偏差（中位） | 4.8 cm | **2.8 cm** |
| 目标超出腿长可及范围 | — | 3/192 帧（已告警） |
| 腿整体朝向变化 | 1.34° | 6.47° |
| 膝盖位置偏差 | 11.6 cm | **6.2 cm** |
| 膝盖抖动（二阶差分中位） | 0.0041 | 0.0043 |
| 脚踝抖动（二阶差分中位） | 0.0091 | 0.0089 |

**代价说清楚**：腿的朝向会变约 6°。这是把髋（来自重定向）和脚（来自素材）都钉死之后的必然结果，不是实现缺陷。膝盖位置反而更接近素材，抖动没有变差，剩下 3.2/2.8 cm 来自那 3 帧超出可及范围的目标。

UI 在「3 · 确认并应用」的高级选项里，名为**足部落点校正**，默认开启；关掉即回到只传方向。

- **Blender 4.5.0 全量通过**：`test_enable_addon` 54 / `test_mock_retarget` 63 / `test_retarget_coordinates` 16 / `test_motion_presets` 26 / `test_orientations` 103 / `test_review_workflow` 43 / `test_review_reload` 5 项检查，0 失败。
- **确定性**：同一份 `RetargetOptions` 连续应用三次，99 条曲线逐位一致（含足部校正）。这点曾经不成立，原因是读取 `pose_bone.head/matrix` 依赖依赖图的刷新时机；现已改为从源数据解析计算。
- **旧安装副本会拦住**：`tools/validate_rig_proportions.py` 会比对 Blender 实际加载的插件路径与本仓库，不一致时直接停止并说明解决办法——否则会拿旧代码测出昨天的数字。

- **未验证**：以上比例与落点数字来自 Rigify 默认生成的骨架，用户自己的骨架需用同一脚本复测；足部校正只在缓存的 192 帧结果上验证，未跑完整的"真实素材 → 捕捉 → 应用"全链路。
